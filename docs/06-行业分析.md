# 行业分析 · 建筑施工安全数字化与 AI 介入

> 配套《设计方案》《报价单》阅读。数据来源标注在每节末尾；GitHub 项目信息为 2026-11-02 实时查询。

## 一、行业现状

### 1.1 政策与监管压力在收紧

- 住建系统近年持续推动“**从人防到智防**”：把安全管理从靠人盯现场，转向靠数据与系统留痕（住建部，2026）。
- 《安全生产法》确立“三管三必须”，安全责任落到具名岗位；《建筑施工安全检查标准》JGJ 59 是现场检查的通用依据。
- 多地住建主管部门在推“**隐患排查—整改—复查—销项**”的闭环治理，要求过程可追溯、责任可倒查（湖北省住建，2026；福建省住建，2026）。

**对我们的意义**：合规压力已经从“查隐患”转向“查闭环是否可信”——这正是本项目的切入点（凭证链 + 完成口径），不是单纯的图像识别。

### 1.2 现场数字化的真实水平

多数施工企业的现状是**有系统、没闭环**：

- 现场安全平台与分包人员台账权限独立，无统一状态视图（本项目 f30）；
- 隐患登记靠手机拍照 + 手打入描述，照片常缺时间与位置（f31）；
- “完成”的口径在分包与监理之间不一致（f50），指标因此虚高；
- 数据更新有周期（试点按 15 分钟，f34），断链时只能用旧数据，且看不出过期（f35）。

**这不是我们编的痛点，是访谈里逐条核过的**——六个岗位分别陈述，交叉验证后保留分歧（见《微专业-事实库》f00–f55）。

## 二、同类方案调研

在 GitHub 与公开渠道检索，找到四类可对标的项目：

### 2.1 Construction-Safety-Risk-Analysis-System（RAG + LLM）

- 仓库：`jensenzhong/Construction-Safety-Risk-Analysis-System-Based-on-RAG-LLM`
- 做什么：基于 **53000+ 真实事故案例（OSHA）** 做语义检索与风险预评估，接 DeepSeek 做分析
- 与我们的差异：**它强在“事前风险预评估”，我们强在“事中凭证链与闭环”**。它回答“这类作业有什么风险”，我们回答“这条隐患的整改证据是否可信、能不能销项”。两者互补：它的案例库可以作为我们的知识库上游。

### 2.2 智安查（智慧工地安全规范问答与风险预警）

- 仓库：`luowei-666/construction-safety-rag`（AIC 人工智能+场景建造创新大赛作品）
- 做什么：RAG 混合检索 + 结构化风险分析 + 检查报告生成
- 与我们的差异：它是**问答与报告**导向，交付物是一份检查报告；我们是**流程与交接**导向，交付物是待人工确认的交接清单。它没有处理“两套完成口径”“状态反复”这类流程性冲突——而这恰是我们访谈里最痛的点（f50、f11）。

### 2.3 SiteSaha-AI（离线工程 RAG 助手）

- 仓库：`HamzaSo-RGB/SiteSaha-AI`
- 做什么：面向施工工程师、招投标、进度款、HSE 法规的**离线** RAG 助手（本地模型 + Streamlit）
- 与我们的差异：它是**知识问答工具**，无业务状态；优势在离线可用的工程化取舍，值得我们借鉴其“本地降级”设计。

### 2.4 QASTRisk（隧道施工风险问答）

- 仓库：`Murry01/QASTRisk`
- 做什么：面向隧道工程的风险识别问答系统
- 与我们的差异：垂直度更高（隧道），但不涉及多角色交接与签核责任。

### 2.5 小结：市场空在哪

| 维度 | 现有方案普遍做法 | 我们的选择 |
|---|---|---|
| 价值锚点 | 识别隐患、生成报告 | **凭证链可追溯 + 交接可追责** |
| 技术形态 | 纯 RAG 问答 | 规则优先 + 模型补缝 |
| 人工位置 | 事后复核 | **事前设卡点，未确认不得推进** |
| 冲突处理 | 不涉及 | 两套口径并列、不合并，交总监裁定 |

**结论：空白不在“能不能识别隐患”，在“整改到底算不算完成、证据链能不能站住”。** 这决定我们做的是流程系统，不是识别工具。

## 三、市场规模：为什么本报告不引用一个具体金额

**先说结论：本报告不写“中国建筑施工安全信息化市场规模 XX 亿元”。**

原因不是懒，是查不到可核验的口径。公开渠道能拿到的智慧工地、施工安全 App、物联网监测类研报，**目录页多、正文付费**，且各家口径互不一致（有的只算硬件，有的含平台服务，有的并入整个智慧工地）。引用一个来源不明的数字，比不写更危险——一旦被追问“这个数哪来的”，整份报告的可信度都会塌。

所以这一节改用**需求侧可验证证据**，这些是能当场核对的：

| 证据类型 | 具体内容 | 可核验性 |
|---|---|---|
| 政策驱动 | 住建系统持续推动“从人防到智防”，多地把隐患“排查—整改—复查—销项”闭环纳入监管要求 | 有公开文件，链接见第五节 |
| 客户已在测的指标 | 超期隐患率 24%、复查等待 3 天、日均 70 条隐患（f00、f12） | 客户台账直接可查 |
| 组织现状 | 现场安全平台与分包台账权限独立，无统一状态视图（f30） | 系统截图可证 |
| 岗位规模 | 一个工区涉及六个岗位角色（f00–f55 访谈） | 访谈记录可证 |
| 同类项目密度 | GitHub 上可检索到 4 个同类开源/学生项目，均为个人或竞赛作品，**无成熟商用产品** | 链接见第五节 |

**这组证据指向的判断**：市场不缺“能识别隐患”的工具，缺的是“能证明整改真的完成了”的系统。前者已经有大量人脸识别、AI 摄像头、巡检 App；后者——凭证链与完成口径——几乎没人做。

## 四、机会判断

### 4.1 切入顺序：先做最可逆的那一段

按业务结果 × 不可逆风险排序：

1. **先做凭证链（REQ-01）**——出错只是多核对一次，风险可逆，且是其他需求的前提；
2. 再做口径统一（REQ-02）——需要组织对齐，排在凭证链之后、先谈后做；
3. 兜底并行（REQ-04）——上线前必须有的转人工机制；
4. 人工签核（REQ-03）是红线，不是功能，任何版本都不得违反。

### 4.2 商业形态：单工区试点 → 可复制

| 维度 | 判断 |
|---|---|
| 切口 | 单施工检查区 + 两家分包，首期预算 16 万量级（f02、f03） |
| 付费方式 | 基础费 + 效果浮动——客户用超期率与复查等待自己算账（详见《报价单》） |
| 复制性 | 凭证链与完成口径是行业通用问题，不是某家特例 |
| 增长路径 | 单工区 → 多工区 → 多项目；二期可转订阅制（持续运营与规则维护） |

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 客户方接口只读、无写能力（f32） | 只产出“建议与草稿”，不承诺落库；写回能力另行立项 |
| 指标基线未测（f01） | 试点前 3 天现场跟班 + 工单时间戳回放补基线 |
| 多角色口径冲突（f50） | 先谈口径再上线，不合并、并列展示 |
| 模型幻觉导致误判 | 规则优先、模型只出草稿；错误不得覆盖原记录（f15） |
| 组织抗拒（怕被追责） | 审计留痕保护执行者：改判也留原因，不是找谁的错 |
