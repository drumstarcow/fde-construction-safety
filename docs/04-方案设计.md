# 设计方案 · 施工隐患与整改闭环协同助手

> 客户：远筑工程（合成训练场景）　版本：v1.0　日期：2026-11-02
> 本文对应课程要求「设计方案」一项，与《报价单》《微专业-事实库》配套阅读。

## 一、问题与目标

**问题不是“想用 AI”，是凭证链断了。** 三个具体异常叠在一起：整改照片对不上原隐患，巡查员反复跑现场核对（f10、f14）；照片缺时间与位置，同一隐患多人上报形成重复工单（f31）；分包按上传照片算完成、监理按现场复查算完成，两套口径并存导致返工（f50）。

**业务目标**（管理层口径，f00）：超期隐患率 24% → 8%；复查等待 3 天 → 1 天。

**本项目要做成的形态**：协同助手——围绕一笔业务，核对来源、生成待人工复核的交接清单；不自动批准、不写入业务系统。分工三段：项目范围核对 → 资料与版本核对 → 交接草稿起草。

## 二、为什么是规则 + 模型，而不是纯模型

三条路比过：

| 路线 | 能解决 | 解决不了 |
|---|---|---|
| 人工优化（检查清单、标准化流程） | 成本最低、无需改造 | 照片本身缺元数据，人再仔细也只能跑现场（f10、f12） |
| 确定性规则（主编号 + 事件时间 + 版本匹配） | 大部分场景，可解释、零幻觉 | 照片时间缺失、描述与编号对不上这类疑难记录（f31） |
| 纯模型 | 能做语义判断 | 会编、不可解释、出错是安全责任问题 |

**结论：规则先做、模型补缝。** 规则层负责关联、去重、版本校验，命中即出结果，不经过模型；模型只做两件事——疑难记录的相关性判断、交接草稿文本生成。模型输出一律标为“建议”，不参与任何判定。

为什么仍然需要模型：需要“字段不规整也能判断相关”的能力，规则写不出来；但正因为会错，所以只出草稿、不出结论。

## 三、系统架构

四层，代码结构与之对应（见第五节）：

```
┌─ 界面层 ────────────────────────────────────────────┐
│ 业务工作台 │ 知识和图谱 │ 证据与引用 │ 执行与审计 │ 场景评估 │
└──────────────────┬──────────────────────────────────┘
┌─ 编排层（三步）───┴──────────────────────────────────┐
│ ① 项目范围核对 → ② 资料与版本核对 → ③ 交接草稿起草    │
│ 每步产出 trace；异常在任一步中止并转人工              │
└──────────────────┬──────────────────────────────────┘
┌─ 能力层 ──────────┴──────────────────────────────────┐
│ 规则引擎（关联/去重/版本） │ 模型层（判断/起草/降级） │ 知识检索（BM25+图谱）│
└──────────────────┬──────────────────────────────────┘
┌─ 数据层 ──────────┴──────────────────────────────────┐
│ 隐患台账 │ 照片元数据 │ 单据版本 │ 状态日志 │ 知识库 │ 审计日志 │
│ 全部只读接入；不写业务系统；断链用只读快照            │
└─────────────────────────────────────────────────────┘
```

## 四、数据契约

| 实体 | 关键字段 | 说明 |
|---|---|---|
| 隐患主记录 | business_id（主键）、event_time、area_code、level（只读）、status、version | version 冲突时不合并，并列给总监裁定（f24） |
| 凭证记录 | photo_id、photo_time、photo_location、uploader、attach_to | attach_to 是本项目的核心产出字段（REQ-01） |
| 交接记录 | handover_id、from_role、to_role、unresolved_items、confirmed_by、confirmed_at | 对方确认接手才算完成（f23） |
| 审计记录 | action、actor、rule_hit、model_suggestion、human_override、signer、at | 六字段齐全才能重建一次处理（f45） |

**权限矩阵（谁能读写）**

| 角色 | 读 | 写 |
|---|---|---|
| 安全巡查员 | 本人相关隐患 | 照片与描述 |
| 整改协调员 | 全部流程数据 | 交接字段、发起复核；**不能签核**（f22） |
| 分包负责人 | 本分包范围 | 服务侧完成凭证 |
| 总监理工程师 | 全部 | 签核销项、可否决上线（f41） |
| 平台工程师 | 全部 | 字段与接口维护，**不做业务操作** |
| 项目安全经理 | 指标与范围 | 预算与试点边界 |

**接口约定**：当前接口只读，可读隐患与提醒，不自动销项、不判定安全合格（f32）；任何写回能力须单独授权并核实。

## 六、知识库与图谱

**49 条知识条目**，分五类：隐患识别 12、整改流程 11、角色治理 10、数据系统 8、指标验收 8。每条含 id、主题、标题、内容、**来源**、关联标签。

**来源标注是风控核心**：来自访谈事实的标 `f10` 这类编号；只写通用常识的标「具体条文待核」，**不编造规范条文**。

**图谱**：89 节点 / 278 关系，六类关系——属于、对应隐患、动作、责任、红线、指标。

**检索**：两段式带降级。关键词层 BM25 + 字符二元组（无网可跑）；有 key 时加向量层并用 RRF 融合；命中后沿图谱走一跳扩展邻居作为上下文。返回必带 `citations`。检索不到直说“知识库里没有”。

## 七、人工责任边界

**三道卡点**：

1. 照片与隐患关联结果出来后，巡查员确认或改判；错误结果不得覆盖原记录（f15）；
2. 交接草稿生成后，整改协调员确认内容完整才可发出；对方确认接手才算交接完成（f23）；
3. 销项与合格判定由总监理工程师签核；AI 建议与人工结论分开存档（f45）。

**红线（任何版本不得违反）**：不自动销项、不判定安全合格、不写业务系统、不覆盖原始记录、不借用账号、不接入未授权接口；重大危险作业现场发现即人工处置（f40）。

## 八、异常与降级

| 异常 | 处理 |
|---|---|
| 模型超时 | 中止本次调用，标“生成失败，可重试”，转人工，不自动重试第二次 |
| 缺数据 | 标“资料不足”进人工修复队列，不猜不补（f33） |
| 版本/状态冲突 | 并列展示两版、不合并，提示需总监裁定（f24） |
| 越权 | 直接拒绝并记录 actor 与请求内容，不静默降级（f41） |
| 重复请求 | business_id + 动作 + 时间窗做幂等键，返回首次结果并标“已复用” |
| 接口断链 | 只读快照 + “暂未更新”提示，重连按业务编号去重补齐（f35） |
| 触发停止条件 | 暂停该笔业务并转人工复盘（f42） |

## 九、评估与验收

五个评估集，与需求一一对应：

| 评估集 | 规模 | 判据 |
|---|---|---|
| 回放集 | 100 条历史隐患 | 照片自动关联率 ≥80%（REQ-01） |
| 口径集 | 同一批单据 | 分包完成时间与监理复查时间可分别输出，分母与周期固定（REQ-02） |
| 异常集 | 4 类 × 3 例 | 全部能转人并标注原因、接手人、确认时间（REQ-04） |
| 人工确认集 | 抽查 10 笔交接 | 未确认不得标记完成（REQ-03） |
| 审计集 | 任取 5 笔 | 可重建处理过程，六字段齐全（REQ-05） |

**三层验证要分开说**：模拟验证（回放集，证明逻辑对）、真实模型验证（异常集，证明模型在真实输入下不失控）、业务验收（试点实跑，证明采用率与收益）。
