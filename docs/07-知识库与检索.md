## 二、每条条目的字段

```json
{
  "id": "K26",
  "topic": "整改流程",
  "title": "交接",
  "content": "交接须含业务编号、当前版本、处理状态、未解决事项、接手人；对方确认接手才算交接完成。",
  "source": "f23",
  "type": "项目制度",
  "rel": ["动作:交接", "红线:接手确认"]
}
```

**source 是风控核心**：每条都标来源。`f23` 表示来自访谈事实；写「通用安全常识，具体条文待核」的，表示只写常识、不引具体条文号——**绝不编造规范条文**。

## 三、图谱怎么建

节点三类：条目节点（49）、主题节点（5）、概念节点（35：动作/角色/隐患/步骤/红线/指标）。
边两类：条目→主题（属于）、条目→概念（按 rel 标签）。

关系类型（就是老师要的“知识图谱关系”）：
```
属于      条目归属哪个主题
对应隐患  条目指向的隐患类型（如 临边防护）
动作      可执行的动作（整改、去重、转人工、交接、降级…）
责任      责任角色（整改协调员、总监理工程师…）
红线      不可违反的约束（人工签核、只读、权限、停止）
指标      对应哪项验收指标
```

## 四、语义检索怎么做（RAG）

两段式，带降级：
1. **关键词层（必须有，无网可跑）**：对 title+content+tags 建 BM25 索引，中文用 jieba 分词或字符二元组（bigram）——不用装依赖也能跑。
2. **向量层（有 key 才启用）**：调用 embedding 接口，把 49 条向量化，查询时算余弦相似度；与 BM25 结果融合（RRF 倒数排名融合，简单有效）。
3. **图谱扩展**：命中条目后，沿 graph.json 的一跳关系扩展邻居节点（同隐患、同动作、同角色），作为上下文补充——这就是“图谱化检索”和普通 RAG 的区别。

返回格式必须带来源：
```json
{"answer": "...", "citations": [{"id": "K26", "title": "交接", "source": "f23"}]}
```
检索不到就直说「知识库里没有」，不许编。

## 五、LangGraph 编排（三个节点）

```
Node1 项目范围核对：校验业务编号是否在授权样本内 → 不在则直接返回“不在范围”，终止
Node2 资料与版本核对：检索知识库(K23/K41/K42)，校验照片元数据与版本一致性
      → 缺数据/冲突则转人工，走“人工修复队列”分支
Node3 交接草稿起草：检索知识库(K26/K27)，生成待确认交接清单
      → 结束，进入人工确认队列（不写业务系统）
```
三个节点共享同一个 state（业务编号、数据版本、检索命中、异常标记、草稿），LangGraph 的 StateGraph 正好表达这个；没有装 langgraph 时，用等价的函数链路实现，接口保持一致。
