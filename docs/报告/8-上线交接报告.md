## 任务2：演练发布与回滚

任务要求：固定交付版本、发布窗口、灰度范围、回滚触发器和步骤，演练一次故障恢复。

核对问题：怎样发现故障、停止影响并恢复到已知可用版本？

预期交付：发布计划与回滚演练记录

### 我的理解与结论

结论：交付版本固定为 git tag，发布窗口选非作业高峰（午休或收工后）；回滚触发器三条，回滚目标为「停服务即回到人工流程」——因为本系统不写业务系统，回退成本接近零。

一、发布计划

项；内容
版本；固定 commit（例：`4ae43ac`）+ tag `v1.0.0-pilot`
窗口；工作日 12:00–13:00 或 18:00 后（避开现场上报高峰）
灰度；先 1 个检查区 → 观察 3 天 → 再开第二区
变更内容；后端 + 前端静态文件；数据文件不迁移（本来就是本地 JSON）
通知；提前一天告知使用者与分包负责人（叶书）

二、回滚触发器

触发条件；动作
自动关联错误被采纳（错误进交接单）；立即停用自动化，回滚到人工核对
服务不可用 >30 分钟；回滚到上一版本
出现越权写操作告警；立即停服，保全审计日志

三、回滚步骤（已演练）

1. 停止服务：systemctl stop（或直接结束 uvicorn 进程）
2. 恢复上一版本代码：git checkout <上一个 tag>
3. 数据：data/*.json 保持不动（审计是追加写，不丢）
4. 启动：uvicorn app:app --port 8000
5. 验证：curl /api/health → degraded 状态是否符合预期；/api/eval 五集是否仍通过
6. 通知：告知使用者已回退，期间的数据人工补录

演练记录：本地演练一次「停服务 → 切旧 tag → 重启 → 健康检查」，用时约 4 分钟；期间现场作业不受影响（因为本来就有纸质流程兜底）。

四、故障怎么被发现

层；发现方式
服务挂；使用者上报 + 健康检查探针（待配）
结果错；人工复核时发现（这是最后一道防线，不能省）
数据断链；界面显式「暂未更新」+ 时间戳（f35）

五、待核实

- 客户方是否有统一监控平台可接入；
- 回滚窗口与现场作业时间的冲突（需顾明岚确认）。

### 标准参考答案

一、发布计划。交付版本应固定为可追溯的代码版本和配置版本，建议使用版本号加提交标识，并在发布记录中登记构建时间、变更内容和回滚目标版本。发布窗口应避开现场上报和整改交接高峰，具体时段需与项目安全经理顾明岚确认；灰度范围建议先覆盖一个检查区，观察期和扩大条件需在发布前写明。发布前应通知安全巡查员、整改协调员和分包负责人叶书，明确试点期间人工流程继续保留。

二、故障发现。故障发现至少包括三类：服务不可用，由使用者上报和健康检查发现；结果错误，由人工复核发现，人工复核是最后防线不能省略；数据断链或过期，由界面显式提示更新时间戳并转人工核对。健康检查探针如尚未配置，应列为发布前准入条件或明确人工巡检替代方案。

三、停止影响与回滚触发器。建议设置三类触发器：自动化结果被人工复核确认错误并已进入交接单时，立即停用自动化并回到人工核对；服务不可用超过约定时长时，回滚到上一已知可用版本；出现越权写操作告警时，立即停服并保全审计日志。回滚决策人和批准恢复上线的责任人需与总监理工程师傅景、项目安全经理顾明岚确认。

四、回滚步骤。停止服务，恢复上一已知可用版本代码和配置，保持审计记录追加写不删除，重启后验证健康检查和关键接口，通知使用者已回退，回滚期间产生的隐患单、整改照片和交接记录由人工补录并标记来源。数据文件是否迁移、回滚后数据一致性如何校验，需由现场平台工程师秦芮确认，不能默认“不迁移即不丢”。

五、演练记录。本次已做本地演练：停服务、切换旧版本、重启、健康检查，用时约四分钟，现场作业因有纸质流程兜底未受影响。待补演练：错误结果被采纳场景、越权写操作告警场景、回滚期间数据补录场景。

六、待核实事项。客户方是否有统一监控平台可接入；发布窗口与现场作业时间的冲突需顾明岚确认；回滚期间交接单状态规则需唐映秋确认；越权告警停服权限和审计留存要求需傅景确认；真实接口和业务验收标准需另行核实。

### 答案对比与判断

学员围绕“演练发布与回滚”给出了较完整的发布计划、回滚触发器、回滚步骤和一次本地演练记录，覆盖了版本固定、发布窗口、灰度范围、故障发现、停止影响和恢复路径，任务主线基本完整。优点是把回滚目标设为“停服务即回到人工流程”，与案例中保留人工确认和纸质兜底的边界一致；也提到通知分包负责人、越权写操作告警时保全审计日志，体现了权限与审计意识。主要不足：一是多处引用未在访谈材料中出现的具体技术细节（如 git tag、systemctl、uvicorn、/api/health、/api/eval 五集、f35 时间戳），这些属于学员自行假设，不能当作已核实事实；二是“数据文件不迁移、审计追加写不丢”的判断缺少依据，回滚后数据一致性和补录责任未说明；三是故障发现层中“健康检查探针（待配）”仍是待办，演练只验证了停服务重启，未覆盖“错误结果被采纳”和“越权写操作”两类触发器的实际演练；四是发布窗口、灰度观察期、回滚决策人未与顾明岚、傅景等角色确认，验收标准和权限边界仍待补；五是未说明回滚期间已产生的整改照片、交接单如何标记和补录，异常闭环不完整。
