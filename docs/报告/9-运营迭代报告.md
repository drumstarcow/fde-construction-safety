### 标准参考答案

一、演练场景与判断
以“照片时间容差由±5分钟放宽到±30分钟”为变更，演练旧关联规则失效：状态反复的临边防护记录被误判为重复，导致重复工单被合并。该场景与“整改照片不能定位到原隐患、巡查员多次现场核对”的问题方向一致，可作为待验证假设，但样本量和评估集规模需用本项目样本建立基线，不能视为已验证数据。

二、事件复盘应包含
1. 发现：巡查员发现同一隐患被错误合并，经整改协调员反馈；记录反馈单、时间、涉及单据。
2. 处置：暂停自动关联，转全人工核对；保全审计日志和原始照片、工单、交接记录。
3. 回滚：回退到上一规则版本，重启后验证关联结果；回滚耗时和验证范围需记录。
4. 根因：时间容差放宽后，状态反复记录被误判为重复；需补充“状态反复”识别规则或白名单。
5. 修复：恢复容差并增加状态反复不合并规则；修复需经人工复核确认。
6. 回归：重跑历史样本并补充状态反复样本；回归集规模待用本项目样本确定，不能虚构100笔等数量。

三、变更管理规则
1. 任何影响关联口径、合并规则、销项状态的变更，上线前必须重跑评估集，任一关键指标退化则阻断上线；评估集和阈值待建基线后确定。
2. 规则版本留档，审计记录规则版本号，确保事后可追溯“当时用的是哪版规则”。
3. 变更前通知使用者并培训，避免现场困惑；变更后收集反馈形成闭环。
4. 知识库条目变更受控：失效条目标注而非直接删除，保留历史引用可追溯。
5. 审计字段只增不改，确需修改则写迁移脚本并保留旧值。
6. 增加灰度发布、双人复核和回滚触发阈值；异常时转人工。

四、旧需求不失效的防护
1. 红线规则做成断言测试，每次回归必跑，如“不自动销项”“不自动合并高风险隐患”。
2. 变更影响分析覆盖关联、合并、销项、通知、审计五类旧需求。
3. 数据结构变更走迁移脚本，历史审计可读。
4. 知识库引用存条目ID而非文本快照，条目失效标注。
5. 试点验收指标包括关联准确率、人工复核率、返工次数、处理时长、版本正确率和采用率，基线待本项目样本建立。
